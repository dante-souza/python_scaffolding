# Python Scaffolding v0.5.1 — Windows env-rebuild Hotfix Archaeology Report

## 1. Scope

This report documents the historical hotfix boundary represented by `v0.5.1`.

**Release:** Windows `env-rebuild` hotfix  
**Boundary commit:** `0d9e5915d8f88124addbc0fe073666a9e99e8ae4`  
**Historical merge:** `merge: fix Windows env-rebuild self-delete`

This report preserves the full debugging sequence because the final code only makes complete sense when both failures are understood:

1. Windows refused to delete the active project interpreter.
2. The first fix released the lock but returned the PowerShell prompt before rebuild output had completed.

The second bug is especially important archaeologically because CI had passed the first hotfix.

---

## 2. Context: Phase 4 migration on a real Windows machine

Phase 4 changed the reusable scaffold default from Conda authority to native uv authority.

On Pangaea, the checkout still contained a project venv created under the older Conda authority.

The first doctor run correctly identified the mismatch:


The repository did not silently reuse the old venv.

That was correct behavior.

## 4. Failure 1: Windows self-delete

The shell prompt showed an active project venv:

```text
(python-scaffolding) (.venv) PS M:\ATOL\GitProjects\python_scaffolding>
```

The command was:

```powershell
make env-rebuild
```

The dispatcher itself was executing from:

```text
M:\ATOL\GitProjects\python_scaffolding\.venv\Scripts\python.exe
```

The implementation attempted:

```python
if VENV.exists():
    print(f"Removing {VENV}")
    shutil.rmtree(VENV)
```

Windows refused to delete the executable that was currently running.

## 6. Why Linux CI had not exposed the bug

Unix-like operating systems generally allow an executable file to be unlinked while a process is still executing it.

Windows does not.

Therefore this sequence:

```text
current process = .venv Python
delete .venv
```

has different platform semantics.

Earlier CI proved setup and check on Windows, but did not intentionally force `.venv` to be the current Python and then ask it to delete itself.

Real-machine validation found a gap in the test model.

## 8. First hotfix design

The first hotfix branch was:

```text
fix/windows-env-rebuild-self-delete
```

The initial strategy was:

```text
detect Windows
detect env-rebuild
detect current Python inside .venv
        |
        v
resolve safe authority Python outside .venv
        |
        v
replace current process
        |
        v
old executable lock disappears
        |
        v
delete and rebuild
```

The key idea was correct: the Python process holding `.venv\Scripts\python.exe` must stop before deletion.

---

## 9. Initial process-replacement implementation

The first version used a process replacement mechanism from Python.

Conceptually:

```python
os.execv(
    str(executable),
    [
        str(executable),
        str(ROOT / "scripts" / "repo.py"),
        "env-rebuild",
    ],
)
```

For native uv authority, the code prepared and resolved the managed Python first.

The replacement target was explicitly required to live outside the project venv.

Unit tests covered:

- Conda escape;
- uv managed-Python preparation;
- no escape for unrelated commands.

CI passed.

That looked like success.

---

## 10. Pangaea exposed Failure 2: prompt/output interleaving

The first hotfix was tested on the actual Windows shell while `.venv` was active.

The file-lock problem was solved.

But the terminal output showed a new defect.

Observed sequence:

```text
(python-scaffolding) (.venv) PS ...> make env-rebuild
Python 3.12 is already installed

(python-scaffolding) (.venv) PS ...> Removing M:\ATOL\GitProjects\python_scaffolding\.venv
+ ...\python.exe ...\scripts\bootstrap.py
...
```

The PowerShell prompt had returned before the rebuild was finished.

The shell believed the foreground command was done while the replacement process continued writing.

---

## 11. The collision became undeniable

A command was typed after the premature prompt:

```powershell
$LASTEXITCODE
```

Output collided with still-running doctor output:

```text
(python-scaffolding) (.venv) PS ...> $LASTEXITCODE
0env_source_conda_prefix=<not recorded>

(python-scaffolding) (.venv) PS ...>
venv_source_matches_authority=True
venv_python_version_matches_authority=True
venv_base_prefix_matches_authority=True
...
```

This was not cosmetic.

Foreground command semantics were broken.

A CLI command must not return control while it is still producing output.

---

## 12. Why the first fix was incomplete

The first design satisfied only one invariant:

```text
old .venv Python must exit before deletion
```

It failed to preserve the second:

```text
the user's foreground parent must wait
until the entire rebuild finishes
```

The required design therefore needed two different process-lifetime roles.

---

## 13. Final design: PowerShell owns foreground lifetime

The corrected design became:

```text
                    Make / PowerShell
                           |
                           | remains alive
                           v
                 short Python resolver
                           |
                    resolves safe Python
                           |
                    resolver exits
                           |
              .venv python.exe lock released
                           |
                           v
                  safe authority Python
                           |
                     delete .venv
                           |
                      bootstrap
                           |
                        sync
                           |
                       doctor
                           |
                           v
                 child process exits
                           |
                           v
                    prompt returns
```

PowerShell does not implement environment policy.

It coordinates process lifetime.

Python still decides which authority interpreter is valid.

---

## 14. Makefile special-case boundary

The final Makefile routes only the destructive Windows rebuild through PowerShell:

```make
PYTHON ?= python
POWERSHELL ?= powershell
PROJECT_CLI := $(PYTHON) scripts/repo.py

ifeq ($(OS),Windows_NT)
ENV_REBUILD_CLI := $(POWERSHELL) -NoProfile -File project.ps1 env-rebuild
else
ENV_REBUILD_CLI := $(PROJECT_CLI) env-rebuild
endif

env-rebuild:
	@$(ENV_REBUILD_CLI)
```

Every other public command remains on the ordinary dispatcher path.

The exception is narrow and platform-specific because the underlying executable-lock rule is narrow and platform-specific.

---

## 15. Private Python target resolver

The final implementation introduced:

```text
scripts/env_rebuild_target.py
```

Its responsibility is only to select a safe authority Python outside the project venv.

### Conda path

It resolves the active Conda Python.

### Native uv path

It:

1. requires native uv;
2. ensures the requested managed Python is installed;
3. resolves the managed interpreter;
4. rejects any target inside the project venv.

Representative guard:

```python
if inside(python, POLICY.venv):
    raise EnvironmentContractError(
        "env-rebuild authority Python resolved inside the project .venv"
    )
```

The resolver prints the safe interpreter path and exits.

That exit is what releases the old project interpreter lock.

---

## 16. PowerShell coordination

The PowerShell adapter handles only the `env-rebuild` command specially.

Representative final logic:

```powershell
$RebuildPythonOutput = & $PythonBin "scripts/env_rebuild_target.py"
$TargetExitCode = $LASTEXITCODE

if ($TargetExitCode -ne 0) {
    $ExitCode = $TargetExitCode
}
else {
    $RebuildPython = [string](
        $RebuildPythonOutput | Select-Object -Last 1
    )
    $RebuildPython = $RebuildPython.Trim()

    & $RebuildPython "scripts/repo.py" @CommandArgs
    $ExitCode = $LASTEXITCODE
}
```

PowerShell remains alive across both child processes.

Therefore the prompt cannot return between resolver and rebuild.

---

## 17. Defensive direct-path guard

The Python dispatcher also rejects unsafe direct invocation on Windows:

```python
if IS_WINDOWS and inside(sys.executable, VENV):
    raise SystemExit(
        "ERROR: Windows env-rebuild cannot delete the project .venv while "
        "running from its Python. Use: make env-rebuild "
        "(or .\\project.ps1 env-rebuild)"
    )
```

This prevents a future caller from bypassing the safe process boundary accidentally.

## 25. Why the failed first fix is worth preserving

A squashed history could make the final solution look obvious:

```text
Windows cannot delete active Python
-> use PowerShell parent
```

That is not what happened.

The actual engineering path was:

```text

   |
   v

   |
   v
escape current Python
   |
   v
CI green
   |
   v

   |
   v

   |
   v
PowerShell remains parent
   |
   v

```

That sequence teaches more than the final diff.

It shows that fixing resource ownership can create synchronization bugs at the next boundary.

## 26. Architectural lesson

The final responsibility split is:

```text
Python:
  environment policy
  authority resolution
  provenance
  rebuild logic

PowerShell:
  Windows foreground process lifetime

Makefile:
  canonical public command
  narrow platform routing for destructive rebuild
```

No layer takes over another layer's job.

The hotfix therefore improved architecture rather than merely inserting a workaround.

## 28. Archaeological summary

`v0.5.1` is the “real Windows shell completed the architecture” release.

The two preserved defects are:

```text
1. self-delete:
   .venv Python cannot delete itself on Windows

2. foreground race:
   releasing the lock is not enough if the prompt returns early
```

The final fix satisfies both:

```text
old project Python exits before deletion
+
PowerShell remains foreground parent until completion
```

That process-lifetime invariant is now protected by code, tests, CI, documentation, and the preserved hotfix history.
