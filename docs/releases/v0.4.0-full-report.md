# Python Scaffolding v0.4.0 — Phase 3 Testing and CI Archaeology Report

## 1. Scope

This report documents the historical boundary represented by `v0.4.0`.

**Phase:** Phase 3 — test the scaffold itself  
**Boundary commit:** `5b4acf822fa5bf26a66cc33dc4dca22bcbe0bdab`  
**Historical merge:** `merge: phase 3 scaffold testing`

By this point the repository had:

- repaired environment invariants;
- centralized environment policy;
- separated shell bootstrap from Python policy;
- introduced Conda authority handoff.

Phase 3 changed the repository from “architecture that looks coherent” into “architecture that is mechanically checked.”

---

## 2. The testing target was the scaffold, not just the sample package

A common template-repository failure is to test only the example application while leaving the scaffolding machinery untested.

Phase 3 inverted that priority.

The critical objects under test became:

```text
environment policy
provenance identity
authority state
dispatcher behavior
Makefile command surface
shell adapters
bootstrap behavior
doctor assumptions
CI lifecycle
```

The sample package remained useful as a smoke target, but it was not the center of the test strategy.

---

## 3. Contract layers

The testing model became layered:

```text
environment.toml
      |
      v
scripts/environment.py
      |
      +--> policy parsing tests
      +--> path/provenance tests
      +--> authority state tests
      |
      v
bootstrap.py / repo.py / doctor.py
      |
      +--> dispatcher tests
      +--> lifecycle tests
      +--> diagnostics tests
      |
      v
Makefile / shell adapters
      |
      +--> command contract tests
      |
      v
GitHub Actions
      |
      +--> Linux execution
      +--> Windows execution
```

This structure made later Phase 4 changes safer because failures could be located at the right layer.

---

## 4. Environment state and provenance tests

The repository gained focused tests around questions such as:

- Is the configured authority actually active?
- Does the current Python live inside the expected prefix?
- Does `.venv` exist?
- Is provenance metadata readable?
- Does recorded source Python match the expected source Python?
- Does version identity match?
- Does path normalization behave across operating systems?

The important principle was fail-closed behavior.

A stale `.venv` should not silently become valid because its directory exists.

---

## 5. Dispatcher tests

The dispatcher was tested as an execution boundary.

Important conditions included:

```text
help works without an authority handoff
unknown commands return usage failure
handoff preserves arguments
handoff child exit code is propagated
no handoff target means no child process
already under authority -> no recursive handoff
local command runs once
```

The purpose was to prove behavior, not only helper return values.

This mattered later when Phase 4 introduced authority-specific dispatch semantics.

---

## 6. Command-surface tests

The Makefile remained canonical.

Tests checked that the public target vocabulary and dispatcher vocabulary stayed aligned.

Conceptually:

```python
makefile_targets() == {"help", *repo_module.TARGETS}
```

and public targets were expected to route through the shared dispatcher rather than gaining ad-hoc recipes.

This is a subtle but important scaffold invariant:

> A command documented for users should exercise the same code path that CI validates.

---

## 7. Shell adapter tests

The adapters were tested for both success and startup failures.

Representative contracts:

### Bash

```text
./project.sh help
  -> delegates to shared dispatcher
```

Missing Python:

```text
ERROR: Python command not found
Pre-Python diagnostics:
...
exit 127
```

### PowerShell

```text
.\project.ps1 help
  -> delegates to shared dispatcher
```

Missing Python likewise returns 127 with pre-Python diagnostics.

OS-specific adapter tests were skipped locally where the host could not exercise the relevant shell and delegated to CI for proof.

---

## 8. CI became part of the architecture

Phase 3 introduced Linux and Windows GitHub Actions coverage.

The important decision was to validate the **repository lifecycle**, not reproduce the lifecycle inside YAML.

The expected high-level flow became:

```text
runner preparation
       |
       v
make setup
       |
       v
make check
```

CI was not allowed to replace this with a custom series such as:

```text
uv sync
pytest
ruff
some extra shell setup
```

unless that behavior was itself part of the public repository contract.

---

## 9. Why Makefile-first CI matters

If CI bypasses the Makefile, two systems emerge:

```text
developer workflow
    make setup
    make check

CI workflow
    completely different commands
```

Both can be green while users are broken.

Phase 3 instead aligned them:

```text
developer
   |
   v
Makefile

CI
   |
   v
Makefile
```

This decision directly exposed Phase 4 bugs later, because the authority lifecycle could not hide behind CI-only commands.

---

## 11. CI responsibilities at this boundary

At `v0.4.0`, CI was responsible for proving:

- repository checkout works on Linux;
- repository checkout works on Windows;
- GNU Make can drive the public lifecycle;
- shell/platform assumptions are explicit;
- setup produces a usable project environment;
- linting passes;
- tests pass;
- agent/skill validation passes.

It did not yet prove both Python authorities, because native uv authority did not yet exist.

---

## 12. Test quality principle: assertions about architecture

Many Phase 3 tests intentionally assert architecture, not just output.

Examples of architectural assertions include:

```text
Makefile target exists
target delegates to shared dispatcher
help does not require authority
handoff is single-pass
provenance mismatch is rejected
shell startup errors have defined exit codes
```

These tests are valuable because refactors can preserve superficial output while violating the intended responsibility split.

---

## 13. Errors Phase 3 was designed to catch

Phase 3's test strategy targeted regression classes such as:

### Policy drift

```text
bootstrap uses one authority rule
doctor uses another
repo.py uses a third
```

### Command drift

```text
Makefile documents target
dispatcher does not implement it
```

### Handoff recursion

```text
bootstrap Python -> authority Python -> authority Python -> ...
```

### False provenance acceptance

```text
.venv exists -> assumed correct
```

### Shell failure ambiguity

```text
Python missing vs Python unusable -> same failure
```

The repository was now prepared to detect these classes automatically.

---

## 14. What v0.4.0 intentionally did not solve

At this tag:

- Conda was still the only Python authority;
- native uv executable resolution did not exist;
- uv-managed Python selection did not exist;
- CI did not yet have a Conda/uv matrix;
- provenance did not yet encode uv-specific identity;
- Windows CI had not yet been taught the active-`.venv` destructive rebuild regression case.

Phase 3 built the proving ground. Phase 4 used it.

---

## 15. Why Phase 3 had to precede Phase 4

Adding native uv changed several dimensions simultaneously:

```text
authority model
interpreter discovery
bootstrap
provenance
sync
lock
doctor
dispatcher behavior
CI
```

Without Phase 3, a failure could be attributed to almost anything.

With Phase 3, the repository already knew what “correct” meant for:

- public commands;
- shell boundaries;
- provenance;
- handoff;
- quality gates.

That made the dual-authority change tractable.

---

## 16. Transition to v0.5.0

The next roadmap step was intentionally delayed until this point:

```text
authority = "uv"
```

Phase 4 would add native uv as a second authority while preserving:

```text
same Makefile vocabulary
same project .venv boundary
same fail-closed provenance philosophy
same quality gates
```

It would also expand CI to four lanes:

```text
Linux / Conda
Linux / uv
Windows / Conda
Windows / uv
```
