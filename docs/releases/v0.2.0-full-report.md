# Python Scaffolding v0.2.0 — Phase 1 Environment Architecture Report

## 1. Scope

This report documents the historical boundary represented by `v0.2.0`.

**Phase:** Phase 1 — extract environment architecture  
**Boundary commit:** `a744e5d53e129bfd9e6de7c5952ba9834cd3e175`  
**Historical merge:** `merge: phase 1 environment architecture`

Phase 0 had repaired the repository's actual invariants. Phase 1 converted those repaired facts into a shared environment architecture.

The phase deliberately did **not** add a second authority. Conda remained the only supported Python authority. The goal was extraction, not expansion.

---

## 2. The problem Phase 1 addressed

Before this phase, repository commands knew environment rules independently.

That creates drift:

```text
bootstrap.py  ---- knows Conda rules
doctor.py     ---- knows Conda rules
repo.py       ---- knows Conda rules
tests         ---- infer those rules again
```

Even when every copy is correct initially, policy changes become risky because several files can disagree.

The target architecture became:

```text
             environment.toml
                    |
                    v
          scripts/environment.py
            /       |        \
           /        |         \
 bootstrap.py   doctor.py   repo.py
```

One declarative source of truth plus one shared interpretation layer.

---

## 3. environment.toml: policy became data

The historical `v0.2.0` policy was:

```toml
# Canonical environment-policy configuration.
# Phase 1 extracts policy from implementation; only the existing Conda authority
# is supported here. Native uv authority is intentionally deferred to Phase 4.

[environment]
authority = "conda"
venv = ".venv"
provenance_file = ".project-source-python.json"

[uv]
invocation = "python-module"
```

Several decisions are encoded here.

### Authority

```toml
authority = "conda"
```

Conda remains responsible for source-interpreter selection.

### Runtime boundary

```toml
venv = ".venv"
```

The project runtime remains a repository-local venv.

### Provenance location

```toml
provenance_file = ".project-source-python.json"
```

The identity evidence remains colocated with the environment it describes.

### uv invocation

```toml
invocation = "python-module"
```

At this phase uv is intentionally invoked through the authority Python:

```text
<conda-python> -m uv
```

rather than treated as a separate Python authority.

## 4. EnvironmentPolicy became the shared model

`scripts/environment.py` introduced a typed policy object:

```python
@dataclass(frozen=True)
class EnvironmentPolicy:
    authority: str
    venv_name: str
    provenance_file: str
    uv_invocation: str

    @property
    def venv(self) -> Path:
        return ROOT / self.venv_name

    @property
    def venv_python(self) -> Path:
        return self.venv / (
            "Scripts/python.exe" if IS_WINDOWS else "bin/python"
        )

    @property
    def provenance_path(self) -> Path:
        return self.venv / self.provenance_file
```

This mattered because callers no longer had to independently reconstruct platform paths or filenames.

## 5. Policy loading failed closed

The loader distinguished invalid repository policy from invalid runtime state.

Representative structure:

```python
try:
    with path.open("rb") as stream:
        raw = tomllib.load(stream)
except OSError as exc:
    raise EnvironmentContractError(
        f"environment policy is unavailable: {path}"
    ) from exc
except tomllib.TOMLDecodeError as exc:
    raise EnvironmentContractError(
        f"environment policy is invalid TOML: {path}"
    ) from exc
```

Missing required fields were collected explicitly:

```python
missing = [
    ...
    ("environment.authority", policy.authority),
    ("environment.venv", policy.venv_name),
    ("environment.provenance_file", policy.provenance_file),
    ("uv.invocation", policy.uv_invocation),
]
```

Representative failure:

```text
environment policy is missing required values:
environment.provenance_file
```

The repository could now distinguish “policy cannot be read” from “environment does not satisfy policy.”

---

## 6. Phase 1 deliberately rejected unsupported policy

The key historical guard was:

```python
if policy.authority != "conda":
    raise EnvironmentContractError(
        f"unsupported environment authority in Phase 1: {policy.authority!r}"
    )
```

This is valuable archaeological evidence.

The design already used the generic term **authority**, but the implementation refused to pretend native uv support existed before it had been designed and proven.

Similarly:

```python
if policy.uv_invocation != "python-module":
    raise EnvironmentContractError(
        f"unsupported uv invocation in Phase 1: {policy.uv_invocation!r}"
    )
```

The schema could express future evolution without silently accepting unimplemented modes.

## 7. Shared path identity

Cross-platform path comparison moved into the environment layer:

```python
def normalized(path: str | Path) -> str:
    return os.path.normcase(os.path.abspath(str(path)))
```

and:

```python
def inside(path, parent) -> bool:
    if not parent:
        return False
    try:
        return (
            os.path.commonpath([normalized(path), normalized(parent)])
            == normalized(parent)
        )
    except ValueError:
        return False
```

That normalized Windows case behavior and handled incompatible-drive comparisons safely.

This helper later became important in the Windows self-delete guard.

## 8. Active authority became a shared concept

The architecture defined:

```python
def active_authority_prefix(policy):
    if policy.authority == "conda":
        value = os.environ.get("CONDA_PREFIX")
        return Path(value) if value else None
    return None
```

and:

```python
def require_active_authority(policy):
    prefix = active_authority_prefix(policy)
    if prefix is None:
        raise EnvironmentContractError(
            "no active conda environment; "
            "activate the intended environment first"
        )
    if not inside(sys.executable, prefix):
        raise EnvironmentContractError(
            "current Python is outside the active conda environment"
        )
    return prefix
```

Commands could now ask the environment layer for authority state rather than repeating Conda-specific logic.

## 9. Provenance became a reusable service

Phase 0 had already enforced provenance.

Phase 1 moved the mechanics into shared functions:

```text
read_provenance()
expected_provenance()
provenance_record()
provenance_matches()
```

The historical expected record remained Conda-specific:

```python
return {
    "source_python": normalized(python_executable),
    "source_python_version": python_version or sys.version.split()[0],
    "source_conda_prefix": normalized(prefix),
}
```

This distinction is important:

> Phase 1 generalized the *architecture* of provenance before generalizing the *authority types*.

That made Phase 4 much smaller and safer.

---

## 10. uv invocation remained authority-local

The helper:

```python
def uv_module_args(policy, *args):
    ...
    return ["-m", "uv", *args]
```

codified the Conda-era invocation rule:

```text
Conda Python
    |
    +--> python -m uv sync
    +--> python -m uv lock
```

Later, native uv would use an executable directly. At this point that distinction was not yet supported.

---

## 11. Error model

Phase 1 introduced `EnvironmentContractError` as the environment-layer failure type.

Representative policy errors:

```text
environment policy is unavailable
environment policy is invalid TOML
environment policy is missing required values
unsupported environment authority in Phase 1
unsupported uv invocation in Phase 1
```

Representative runtime errors:

```text
no active conda environment;
activate the intended environment first
```

```text
current Python is outside the active conda environment
```

Representative provenance failure remained fail-closed:

```text
project .venv provenance does not match the configured authority
```

The architectural gain was that these concepts now had one owner.

## 12. Responsibility split at v0.2.0

The resulting boundary was:

```text
environment.toml
    declarative policy
          |
          v
environment.py
    policy semantics
    path semantics
    authority state
    provenance semantics
          |
          +--------------------+
          |                    |
          v                    v
bootstrap / repo             doctor
actions                      observation
```

That split is the defining feature of `v0.2.0`.

---

## 13. What Phase 1 intentionally did not solve

The tag still had important limitations:

- Conda remained the only authority;
- `python.request` was not yet part of the policy model;
- native uv executable discovery did not exist;
- uv-managed Python installation/discovery did not exist;
- PowerShell had not yet been promoted to a fully documented bootstrap peer;
- pre-Python diagnostics had not yet been formalized;
- CI did not yet prove the public command contract across operating systems.

These became later roadmap phases.

---

## 14. Why architecture extraction came before uv authority

It would have been easy to add `authority = "uv"` immediately.

That would have forced one patch to solve both:

1. where environment policy lives;
2. how two authorities differ.

Instead, Phase 1 held authority behavior constant and changed only ownership:

```text
Phase 0:
Conda rules distributed

Phase 1:
same Conda rules
one policy model

Phase 4:
same policy model
two authorities
```

That sequencing reduced the search space for every later bug.

---

## 15. Transition to v0.3.0

Once environment policy had a single Python owner, the next architectural question became:

> What is allowed to happen before that Python layer starts?

The answer could no longer be “put environment policy into every shell script.”

Phase 2 therefore established thin Bash and PowerShell bootstrap adapters, startup diagnostics, explicit startup exit codes, and a handoff boundary.
