# Python Scaffolding v0.1.0 — Phase 0 Engineering Archaeology Report

## 1. Scope

This report documents the historical boundary represented by `v0.1.0`.

**Phase:** Phase 0 — repair current invariants  
**Boundary commit:** `046632da7d05ec5e1bf6c16c86c415d6576f75d6`  
**Historical merge:** `merge: phase 0 repair current invariants`

The purpose of this release was not to add a new architecture. It was to make the repository internally trustworthy enough that later architecture could be extracted without preserving contradictions as abstractions.

The main repair areas were:

- license/metadata consistency;
- agent/skill reference and validator correctness;
- reproducible dependency state through `uv.lock`;
- safe repository cleaning;
- accurate Python compatibility declaration;
- project-environment provenance checks.

This report intentionally describes the repository as it existed at the `v0.1.0` tag. Features introduced later, such as `environment.toml`, native-uv authority, PowerShell bootstrap coordination, four-lane CI, and the Windows `env-rebuild` hotfix, are outside this release and are mentioned only as later consequences.

---

## 2. Why Phase 0 existed

The project already had useful behavior, but several contracts were implicit or inconsistent.

The danger was straightforward:

```text
existing implementation
        |
        | contains contradictions
        v
extract architecture
        |
        v
contradictions become "design"
```

Phase 0 reversed that order:

```text
repair facts first
       |
       v
establish invariants
       |
       v
extract architecture later
```

That sequencing became one of the most important decisions in the project.

---

## 3. Canonical command interface at v0.1.0

The Makefile was already the human-facing command contract.

Representative excerpt from the tag:

```make
PYTHON ?= python
PROJECT_CLI := $(PYTHON) scripts/repo.py

doctor:
	@$(PROJECT_CLI) doctor

bootstrap:
	@$(PROJECT_CLI) bootstrap

setup:
	@$(PROJECT_CLI) setup

env-rebuild:
	@$(PROJECT_CLI) env-rebuild

check:
	@$(PROJECT_CLI) check
```

The important invariant was not the exact implementation of every command. It was that users should enter through one stable vocabulary:

```text
make doctor
make setup
make sync
make env-rebuild
make test
make lint
make check
make run
```

At this historical point, the comments still made the environment model explicit:

```text
Conda chooses Python.
uv is managed inside the active Conda environment.
```

Native uv as a Python authority did not exist yet.

---

## 4. Python compatibility was separated from interpreter selection

At the tag, `pyproject.toml` declared:

```toml
[project]
name = "project-template"
version = "0.1.0"
requires-python = ">=3.11"
```

with the accompanying repository rule:

```text
requires-python declares compatibility;
the active Conda environment still selects
the exact interpreter/version used by project automation.
```

This distinction later became fundamental to dual-authority support.

`requires-python` answers:

> Which Python versions may run this project?

It does not answer:

> Which interpreter is the authority for this checkout?

Phase 0 repaired that conceptual separation before Phase 1 formalized it.

---

## 5. Provenance moved from assumption to contract

The major environment-safety improvement was that project commands stopped treating an existing `.venv` as sufficient evidence of correctness.

At `v0.1.0`, `scripts/repo.py` required the active Conda environment and compared it against metadata stored in:

```text
.venv/.project-source-python.json
```

The expected identity was conceptually:

```json
{
  "source_python": "<active-conda-python>",
  "source_python_version": "<version>",
  "source_conda_prefix": "<active-conda-prefix>"
}
```

The implementation normalized paths before comparison:

```python
expected = {
    "source_python": normalized(sys.executable),
    "source_python_version": sys.version.split()[0],
    "source_conda_prefix": normalized(conda_prefix),
}
```

and compared the recorded environment against that expected source.

If the metadata was missing or malformed:

```text
ERROR: project .venv provenance is missing or invalid.
Run: make env-rebuild
```

If it belonged to a different source interpreter:

```text
ERROR: project .venv provenance does not match the active Conda Python.
Run: make env-rebuild
```

This fail-closed behavior survived every later architectural phase.

---

## 6. Conda authority was explicit

The Phase 0 dispatcher did not accept “Conda seems to be installed” as authority.

It required:

1. `CONDA_PREFIX` to exist;
2. the current Python executable to actually live inside that prefix.

Representative implementation:

```python
prefix = os.environ.get("CONDA_PREFIX")
if not prefix:
    raise SystemExit("ERROR: activate the intended Conda environment first.")

common = os.path.commonpath(
    [os.path.abspath(sys.executable), os.path.abspath(prefix)]
)
if os.path.normcase(common) != os.path.normcase(os.path.abspath(prefix)):
    raise SystemExit(
        "ERROR: current Python is not inside the active Conda environment."
    )
```

This protected against shells where Conda-related environment variables and the actual running Python had drifted apart.

## 7. The clean target was deliberately bounded

A repository-cleaning bug can be destructive when the project contains a managed interpreter tree.

The Phase 0 implementation explicitly avoided recursively walking the entire repository.

Representative comment from `scripts/repo.py`:

```python
# Never recurse through the whole repository: doing so reaches .venv and can
# delete interpreter/package caches that belong to the managed environment.
```

The cleaner removed known generated directories and searched only bounded project areas:

```python
for base in (ROOT / "src", ROOT / "tests", ROOT / "scripts"):
    ...
    for p in base.rglob("__pycache__"):
        ...
    for p in base.rglob("*.egg-info"):
        ...
```

The invariant was:

> `make clean` removes generated repository artifacts, not the managed project environment.

The destructive environment operation remained `make env-rebuild`.

---

## 8. Reproducibility: uv.lock became repository state

Phase 0 committed `uv.lock` as part of the project contract.

That was important because the repository was already positioning uv as the dependency-management mechanism, even though Python selection still belonged to Conda.

The lifecycle was conceptually:

```text
Conda selects Python
        |
        v
uv runs inside that authority
        |
        v
uv.lock defines resolved dependency state
        |
        v
.venv is synchronized from that state
```

This prevented later bootstrap work from starting with an ambiguous dependency baseline.

---

## 9. Agent/skill layer was repaired, not expanded

The repository includes a minimal AI agent/skill scaffold.

Phase 0 repaired references and validation so the layer had a consistent canonical shape.

The important scope decision was restraint: this repository is a Python project scaffold, not the place to turn the AI-agent layer into its own platform.

That scope continues into later releases.

---

## 10. Representative command behavior

The intended healthy lifecycle at this phase was:

```text
activate intended Conda environment
        |
        v
make doctor
        |
        v
make setup
        |
        +--> bootstrap
        +--> sync
        +--> doctor
        |
        v
make check
```

The dispatcher intentionally rejected common invalid states.

### No active Conda environment

```text
ERROR: activate the intended Conda environment first.
```

### Python not inside active Conda prefix

```text
ERROR: current Python is not inside the active Conda environment.
```

### Missing project venv

```text
ERROR: project .venv is missing.
Run: make setup
```

### Stale or foreign venv

```text
ERROR: project .venv provenance does not match the active Conda Python.
Run: make env-rebuild
```

These were not UX decorations; they were the first explicit environment invariants.

---

## 11. What Phase 0 intentionally did not solve

At this boundary:

- environment policy was still distributed across implementation;
- there was no `environment.toml`;
- Conda was the only supported Python authority;
- Bash existed as the shell adapter, but PowerShell parity was not yet complete;
- there was no Linux/Windows CI matrix;
- native uv did not select Python;
- shell/bootstrap responsibilities had not yet been formally separated.

Those limitations were intentional roadmap boundaries rather than forgotten work.

---

## 12. Why v0.1.0 is a meaningful archaeological marker

This tag marks the last important point before environment policy was extracted.

It answers a useful historical question:

> What did the repository actually believe before `environment.toml` existed?

The answer was already fairly strong:

```text
Makefile is canonical
Conda selects Python
uv manages dependencies
.venv is project runtime
uv.lock is repository state
provenance must match authority
clean must not destroy .venv
```

Phase 1 did not invent those ideas. It centralized them.

---

## 13. Transition to v0.2.0

The pressure created by Phase 0 was duplication.

Multiple commands needed to know:

- what the authority was;
- where `.venv` lived;
- how provenance was represented;
- how path identity was normalized;
- how uv should be invoked.

The next phase therefore extracted those facts into:

```text
environment.toml
        +
scripts/environment.py
```

That is the architectural boundary represented by `v0.2.0`.
