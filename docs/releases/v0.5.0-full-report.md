# Python Scaffolding v0.5.0 — Phase 4 Dual-Authority Engineering Report

## 1. Scope

This report documents the historical boundary represented by `v0.5.0`.

**Phase:** Phase 4 — dual Python authority  
**Boundary commit:** `5ce2357a5dc2c69a8f96b89c3aa72fb566b5bd82`  
**Historical merge:** `merge: phase 4 dual Python authority`

Phase 4 introduced native uv as a first-class Python authority while retaining Conda.

This was the largest architectural phase because it changed interpreter selection without changing the public Makefile contract.

The design goal was:

```text
same repository
same commands
same .venv boundary
same provenance philosophy
two authority models
```

---

## 2. Final authority model

The repository supports:

```toml
[environment]
authority = "uv"
```

or:

```toml
[environment]
authority = "conda"
```

Native uv became the default for the reusable scaffold.

Conda remained a supported first-class alternative.

The public command vocabulary did not fork.

---

## 3. Compatibility and authority remained separate

The project still uses `requires-python` only as a compatibility declaration.

The exact interpreter selection is controlled separately.

The final policy includes:

```toml
[environment]
authority = "uv"
venv = ".venv"
provenance_file = ".project-source-python.json"

[python]
request = "3.12"

[uv]
invocation = "python-module"
```

The important distinction is:

```text
requires-python >= 3.11
        |
        | compatibility
        v
many allowed versions

python.request = 3.12
        |
        | automation selection policy
        v
authority chooses concrete 3.12 interpreter
```

No `.python-version` was required to conflate those responsibilities.

---

## 4. Authority semantics differ

Conda and native uv are not modeled as if they were the same thing.

### Conda

Conda authority is represented by active shell state:

```text
CONDA_PREFIX
    |
    v
active Conda Python
```

The dispatcher may hand execution to that interpreter.

uv operations run authority-locally through:

```text
<conda-python> -m uv
```

### Native uv

Native uv authority is explicit:

```text
uv executable on PATH
        |
        v
uv-managed Python request
        |
        v
resolved managed interpreter
```

There is no fake “active uv environment.”

The dispatcher does not perform Conda-style re-execution merely because `authority = "uv"`.

---

## 5. Phase 4 sub-blocks

The work was deliberately broken into smaller proofs.

### Phase 4A — model native uv authority

The policy layer learned that authority could be either:

```text
conda
uv
```

without yet assuming the entire lifecycle was complete.

### Phase 4B — resolve native uv managed Python

The environment layer learned to:

- require native uv on PATH;
- install a requested managed Python;
- discover the managed interpreter;
- query its version.

### Phase 4C — bootstrap both authorities

Bootstrap learned to create the project `.venv` from either authority source and record authority-specific provenance.

### Phase 4D — authority-aware lifecycle

sync, lock, dispatcher, provenance validation, and doctor became authority-aware.

### Phase 4E — prove the same Makefile contract

The CI matrix expanded to Linux/Windows × Conda/uv.

---

## 6. Native uv discovery

The final managed-Python discovery contract became:

```python
def uv_python_find_args(policy):
    return [
        "python",
        "find",
        policy.python_request,
        "--managed-python",
        "--system",
        "--no-python-downloads",
        "--no-project",
    ]
```

Equivalent command shape:

```text
uv python find 3.12
  --managed-python
  --system
  --no-python-downloads
  --no-project
```

Every flag is intentional.

---

## 7. Native uv bootstrap flow

The native-uv path became:

```text
require uv executable
        |
        v
uv --version
        |
        v
uv python install 3.12
        |
        v
resolve managed Python
        |
        v
query Python version
        |
        v
uv venv .venv --python <managed-python>
        |
        v
write provenance
        |
        v
uv sync --python .venv/<python>
```

The project runtime is still `.venv`.

The uv-managed interpreter is the source authority.

---

## 8. uv-specific provenance

Native uv provenance records:

```json
{
  "source_authority": "uv",
  "source_python": "<managed-python>",
  "source_python_version": "3.12.15",
  "source_uv_request": "3.12",
  "uv_invocation": "<uv executable>"
}
```

Conda provenance continues to record:

```json
{
  "source_authority": "conda",
  "source_python": "<conda-python>",
  "source_python_version": "<version>",
  "source_conda_prefix": "<prefix>"
}
```

The shared principle is exact source identity.

## 9. The first four-lane proof failed

The initial Phase 4E CI run exposed a real bug.

The failures occurred in:

```text
Linux / uv
Windows / uv
```

while Conda lanes passed.

Bootstrap successfully installed managed Python and created the venv.

Then provenance validation failed:

```text
ERROR: project .venv provenance does not match
the configured Uv Python authority.
Run: make env-rebuild
```

This looked paradoxical because bootstrap had just created the venv.

The fail-closed check was correct.

The rediscovery logic was wrong.

---

## 10. Root cause: project venv contaminated authority discovery

Before `.venv` existed, uv discovery found the managed installation.

After `.venv` existed, a later `uv python find` invocation could resolve the project venv instead.

The state became:

```text
bootstrap provenance:
source_python = uv-managed installation

later authority discovery:
authority_python = project .venv Python
```

The repository correctly rejected that mismatch.

The project venv had accidentally become eligible to impersonate the authority that created it.

---

## 11. Corrective invariant: --system

The fix did **not** weaken provenance.

Instead, authority discovery was constrained so the project environment cannot be selected as the authority.

The corrective argument was:

```text
--system
```

Regression tests explicitly assert it.

The invariant became:

> Native uv authority must resolve a managed source Python outside the project venv.

This was committed in:

```text
e29b2aa phase 4E: keep uv authority outside project venv
```

---

## 12. Why --no-project is not enough by itself

The final command also uses:

```text
--no-project
```

to avoid project configuration affecting discovery.

However the Phase 4 regression demonstrated that authority discovery also needs a source-location boundary.

`--system` enforces the important separation:

```text
authority Python
      !=
project .venv Python
```

---

## 13. Authority-aware sync

The sync path became:

### Conda

```text
<conda-python> -m uv sync --python <project-venv-python>
```

### Native uv

```text
<native-uv> sync --python <project-venv-python>
```

In both cases dependencies land in the same project runtime boundary.

---

## 14. Authority-aware lock

Locking uses the authority Python, not the project venv as an accidental source selector.

Conceptually:

```text
configured authority
      |
      v
source interpreter
      |
      v
uv lock --python <source interpreter>
```

This preserves the distinction between dependency resolution policy and runtime environment contents.

---

## 15. Dispatcher behavior

Phase 4 preserved the Conda handoff model but explicitly prevented native uv from imitating it.

Representative rule:

```python
if POLICY.authority == "uv":
    return None
```

for dispatcher handoff.

Native uv consumers explicitly resolve and pass the managed Python instead.

This avoids inventing shell activation semantics that uv authority does not have.

---

## 16. Four-lane CI

The final Phase 4 matrix became:

```text
Linux / Conda / Make
Linux / uv / Make
Windows / Conda / Make
Windows / uv / Make
```

Each lane performs only runner-specific preparation before entering the same repository lifecycle:

```text
make setup
make check
```

The Conda lane temporarily selects:

```toml
authority = "conda"
```

The uv lane uses the repository default:

```toml
authority = "uv"
```

This proves the same Makefile contract rather than four separate implementations.

## 18. Healthy native-uv doctor state

A correct native-uv state reports the source authority and project runtime separately.

Representative healthy output:

```text
environment_authority=uv
python_request=3.12

authority_python=...uv-managed...\python.exe
authority_python_version=3.12.15

venv_python=...\.venv\Scripts\python.exe
venv_python_version=3.12.15

venv_source_authority=uv
venv_source_python=...uv-managed...\python.exe
venv_source_uv_request=3.12

venv_source_matches_authority=True
venv_python_version_matches_authority=True
venv_base_prefix_matches_authority=True

Environment contract: OK
```

The bootstrap Python can be different from both and still be valid.

## 19. Migration behavior was intentionally fail-closed

When a checkout switches from Conda authority to uv authority, an existing Conda-created venv must not silently survive as if nothing changed.

The expected behavior is:

```text
existing .venv provenance = conda
configured authority      = uv
        |
        v
mismatch
        |
        v
ACTION: make env-rebuild
```

That exact migration later exposed the Windows self-delete bug documented in `v0.5.1`.

---

## 20. What v0.5.0 had not yet discovered

At the Phase 4 boundary, CI was green and the architecture was internally consistent.

However one Windows-specific human workflow had not yet been modeled:

```text
.venv is active
        |
        v
make env-rebuild
        |
        v
current Python is inside the directory being deleted
```

Unix permits unlinking an executing file.

Windows does not.

The next release exists because real-machine migration validation exposed that difference.

---

## 21. Transition to v0.5.1

On Pangaea, the existing project venv had legacy Conda provenance.

Native-uv policy correctly demanded rebuild.

Running that rebuild while `.venv` was active produced:

```text
PermissionError: [WinError 5] Access is denied:
...\.venv\Scripts\python.exe
```

The first fix solved the lock but introduced a foreground prompt race.

The final fix changed the process-lifetime boundary.

That sequence is the subject of the `v0.5.1` archaeological report.
