# Python Scaffolding v0.3.0 — Phase 2 Bootstrap Boundary Report

## 1. Scope

This report documents the historical boundary represented by `v0.3.0`.

**Phase:** Phase 2 — bootstrap boundaries  
**Boundary commit:** `a51535486c16b66b9912ecbf1f9a42448e276135`  
**Historical merge:** `merge: phase 2 bootstrap boundaries`

Phase 1 had centralized environment policy in Python. Phase 2 answered the next question:

> What should Bash and PowerShell do before the shared Python policy layer can run?

The answer was intentionally narrow: resolve enough runtime context to start Python, report failures that occur before Python can start, then delegate.

---

## 2. The boundary problem

Without a clear boundary, shell adapters tend to accumulate policy:

```text
project.sh:
  activate env?
  find uv?
  inspect venv?
  choose Python?
  validate provenance?

project.ps1:
  reimplement all of the above differently?
```

That would recreate the duplication Phase 1 had just removed.

The Phase 2 architecture became:

```text
Makefile / project.sh / project.ps1
                |
                | bootstrap only
                v
        compatible Python starts
                |
                v
          scripts/repo.py
                |
                v
        shared environment.py
```

The shell layer gets Python started. Python owns environment policy.

---

## 3. PowerShell became a first-class adapter

At `v0.3.0`, `project.ps1` resolved:

```powershell
$RootDir = $PSScriptRoot
$PythonBin = if ($env:PYTHON) { $env:PYTHON } else { "python" }
```

The script supported an explicit `PYTHON` override without hard-coding a particular interpreter path.

It resolved the command:

```powershell
$PythonCommand = Get-Command $PythonBin -ErrorAction SilentlyContinue |
    Select-Object -First 1
```

and probed whether it could actually start:

```powershell
$ProbeOutput = & $PythonBin -c "import sys; print(sys.executable)" 2>&1
$ProbeExitCode = $LASTEXITCODE
```

Only after that preflight did it execute:

```powershell
& $PythonBin "scripts/repo.py" @CommandArgs
```

---

## 4. Bash retained the same responsibility

The Bash adapter used the equivalent concepts:

```bash
PYTHON_BIN="${PYTHON:-python}"

if ! PYTHON_RESOLVED="$(command -v "$PYTHON_BIN" 2>/dev/null)"; then
    ...
fi

PYTHON_PROBE_OUTPUT="$("$PYTHON_BIN" -c 'import sys; print(sys.executable)' 2>&1)"
```

Then it delegated to the shared dispatcher.

The architectural rule was parity of responsibility, not identical shell syntax.

---

## 5. Pre-Python diagnostics

The adapters deliberately expose just enough context to debug startup failures.

PowerShell reports:

```text
Pre-Python diagnostics:
  adapter=project.ps1
  repo_root=<path>
  shell=PowerShell <version>
  python_command=<requested command>
  python_resolved=<resolved path>
  conda_prefix=<value or not set>
  virtual_env=<value or not set>
```

Bash reports equivalent context plus shell-specific state such as:

```text
msystem=<...>
wsl_distro=<...>
```

This is not a replacement for `make doctor`.

It exists specifically because doctor cannot help when Python itself cannot start.

---

## 6. Exit code contract

The bootstrap layer adopted conventional startup meanings.

### Exit 127 — command not found

If the requested Python command cannot be resolved:

```text
ERROR: Python command not found: <command>
Pre-Python diagnostics:
...
ACTION: activate the intended Python environment in this shell
or set PYTHON to its interpreter.
```

Exit:

```text
127
```

### Exit 126 — command found but unusable

If the command resolves but cannot start successfully:

```text
ERROR: Python command was found but could not be started successfully.
Pre-Python diagnostics:
...
python_probe_exit=<code>
python_probe_output=<captured error>
ACTION: activate the intended Python environment in this shell
or set PYTHON to a compatible interpreter.
```

Exit:

```text
126
```

This distinction makes startup failures machine-readable as well as human-readable.

---

## 7. WSL was treated as a real execution boundary

The Bash adapter explicitly considered WSL.

When a Python probe fails under WSL, the startup contract explains that a Windows/Cygwin executable inherited through PATH is not automatically a usable WSL interpreter.

The point is architectural:

> PATH visibility and executable compatibility are not the same thing.

That same principle later appears in authority provenance: existence does not prove suitability.

---

## 8. Dispatcher handoff under Conda

Phase 2 also formalized a successful-startup handoff boundary.

The bootstrap Python only needs to be compatible enough to start the shared dispatcher.

If the active Conda authority points to another interpreter, the dispatcher can hand the command to that authority Python.

Conceptually:

```text
shell bootstrap Python
        |
        v
scripts/repo.py
        |
        | authority_handoff_target()
        v
active Conda Python
        |
        v
same requested command
```

This prevents shell scripts from embedding Conda policy.

---

## 9. Single-pass handoff

The handoff contract was designed to avoid recursion.

The selector returns a target only when:

- an authority interpreter exists;
- it differs from the current interpreter.

Once the dispatcher is already executing under the authority Python, the target becomes `None`.

The intended proof conditions were:

```text
no target -> no handoff subprocess
target -> preserve command arguments
child exit -> propagate child exit code
handoff happened -> bootstrap Python does not run command locally
already authority -> command runs exactly once
help -> remains available without authority handoff
```

This became explicit test coverage as Phase 2 closed.

---

## 10. Shell layer: allowed responsibilities

At this tag, the shell layer may:

- find the repository root;
- find the requested Python command;
- test that Python starts;
- print minimal startup diagnostics;
- pass the requested command through;
- preserve the delegated command's exit code.

It must not:

- parse `environment.toml`;
- decide authority validity;
- inspect or repair uv;
- validate `.venv` provenance;
- duplicate doctor.

That division is the defining architectural artifact of `v0.3.0`.

---

## 11. Representative PowerShell control flow

The historical adapter ended with:

```powershell
$CommandArgs = @($args)

if ($CommandArgs.Count -eq 0) {
    $CommandArgs = @("help")
}

Push-Location $RootDir

try {
    & $PythonBin "scripts/repo.py" @CommandArgs
    $ExitCode = $LASTEXITCODE
}
finally {
    Pop-Location
}

if ($null -eq $ExitCode) {
    $ExitCode = 0
}

exit $ExitCode
```

Several small details matter:

- default command is `help`;
- execution occurs from repository root;
- location is restored;
- child exit code is preserved.

---

## 12. Why doctor stayed in Python

A tempting Phase 2 implementation would have replicated the doctor suite in Bash and PowerShell.

That was rejected.

The shell adapters know whether Python can start.

Once Python starts, richer diagnostics belong in one implementation:

```text
scripts/doctor.py
```

This avoids output and policy divergence across shells.

---

## 13. Error classes at this boundary

The repository now had three distinct diagnostic layers.

### Layer 1 — shell startup

Examples:

```text
Python command not found              -> 127
Python found but cannot start         -> 126
```

### Layer 2 — environment policy

Examples:

```text
no active conda environment
current Python outside authority prefix
invalid environment policy
```

### Layer 3 — project runtime/provenance

Examples:

```text
project .venv missing
provenance missing
provenance mismatch
```

That separation made later tests much more precise.

---

## 14. What v0.3.0 intentionally did not solve

Phase 2 still did not provide:

- Linux/Windows CI proof;
- a comprehensive command-contract test suite;
- native uv authority;
- uv-managed Python selection;
- four-lane authority/OS validation;
- Windows-safe self-deletion of an active project venv.

The shell boundary had been designed, but the repository had not yet proven itself across hosts.

---

## 15. Transition to v0.4.0

Once the architecture had:

- centralized policy;
- explicit shell boundaries;
- explicit handoff;

the next risk was regression.

Phase 3 therefore made the scaffold itself the test subject.

The target was not only unit tests for helper functions. It was proof that users and CI execute the same public contract.
