# Python Scaffolding v1.0.0 — Engineering History, Validation, Failures, and Release Report

## 1. Purpose

This report records the engineering path that produced the first stable release of the Python Scaffolding repository.

It is intentionally more detailed than normal release notes. The repository is treated as software archaeology as well as reusable infrastructure, so the report preserves:

- the original phased roadmap;
- the responsibility of each phase;
- the architecture that emerged;
- important code contracts;
- CI validation;
- failures discovered during implementation;
- failures found only on real Windows hardware;
- the unsuccessful first Windows hotfix design;
- the final PowerShell foreground-process correction;
- the SemVer mapping used for the historical releases;
- the exact release boundaries used by the tags.

The final stable release is `v1.0.0`.

## 3. Original roadmap

The roadmap was:

### Phase 0 — repair current invariants

Repair existing contradictions before extracting architecture:

- AGPL/MIT mismatch;
- broken agent references and validation;
- missing `uv.lock`;
- unsafe/incomplete cleaning;
- inaccurate Python compatibility;
- environment-sensitive commands that did not verify interpreter provenance.

### Phase 1 — extract the architecture

Introduce:

- `environment.toml`;
- a shared `scripts/environment.py`;
- one source of truth for Python authority, venv identity, uv invocation, and provenance.

### Phase 2 — fix bootstrap boundaries

Add:

- thin `project.ps1` beside `project.sh`;
- minimal pre-Python diagnostics;
- explicit startup exit codes;
- authority handoff behavior;
- keep the actual doctor in Python.

### Phase 3 — test the scaffold itself

Add:

- unit tests for environment state/provenance;
- integration tests for command surfaces;
- Linux CI;
- Windows CI.

### Phase 4 — add native uv authority

Only after the previous contract was proven:

- introduce `authority = "uv"`;
- keep Conda as a first-class alternative;
- prove the same Makefile contract in both modes;
- make native uv the default only after the dual-mode lifecycle passed.

This sequencing mattered. Phase 4 was not allowed to become an excuse to rewrite the repository before the older invariants, architecture, bootstrap boundaries, and tests were stable.

## 4. Final architecture

The stable architecture is:

```text
                         environment.toml
                          /            \
                         /              \
               authority = uv      authority = conda
                      |                   |
              native uv on PATH      active Conda env
                      |                   |
              uv-managed Python       Conda Python
                       \                 /
                        \               /
                         project .venv
                         |            |
                project dependencies  provenance
                         |
                  scripts/repo.py
                  /      |       \
             Makefile project.sh project.ps1
```

### Public interface

The canonical human-facing interface is the Makefile.

Examples:

```text
make doctor
make setup
make sync
make env-rebuild
make test
make lint
make check
make run
```

The Bash and PowerShell adapters expose the same command vocabulary but are not independent implementations of project behavior.

### Policy layer

`environment.toml` declares policy.

`scripts/environment.py` interprets:

- configured authority;
- Python request;
- native uv resolution;
- Conda authority resolution;
- managed-Python discovery;
- project `.venv` paths;
- provenance generation and comparison;
- authority handoff selection.

### Runtime layer

The project runtime is always the repository `.venv`.

The authority chooses the source interpreter. The project venv contains project dependencies.

This distinction is central:

```text
source authority Python  !=  project .venv Python
```

The venv is attributable to its source through provenance metadata.

## 6. Phase 1 — v0.2.0

Boundary:

```text
a744e5d merge: phase 1 environment architecture
```

Phase 1 introduced the declarative/implementation split.

### Declarative policy

```toml
[environment]
authority = "conda"
venv = ".venv"
provenance_file = ".project-source-python.json"

[python]
request = "3.12"

[uv]
invocation = "python-module"
```

At this point Conda was intentionally still the sole authority.

### Shared implementation

Instead of encoding Conda behavior independently in bootstrap, doctor, and repository commands, `scripts/environment.py` became the common interpretation layer.

This gave later phases a place to add a second authority without creating a second scaffold.

### Provenance contract

The project venv began recording where it came from.

Conceptually:

```json
{
  "source_python": "...",
  "source_python_version": "...",
  "source_conda_prefix": "...",
  "source_authority": "conda"
}
```

The repository could now distinguish:

- a venv that merely existed;
- a venv that was actually produced by the configured authority.

## 7. Phase 2 — v0.3.0

Boundary:

```text
a515354 merge: phase 2 bootstrap boundaries
```

Phase 2 established the shell/Python boundary.

### Shell responsibility

The shell adapters may:

- resolve the repository root;
- resolve the requested Python command;
- verify that Python starts;
- report minimal pre-Python diagnostics;
- preserve exit codes.

They must not become a second implementation of environment policy.

### Startup exit codes

The adapters distinguish:

```text
126 = Python command was found but could not be started
127 = Python command could not be resolved
```

This is useful because “not found” and “found but unusable” are different failure classes.

### PowerShell parity

`project.ps1` was introduced beside `project.sh`.

The stable conceptual boundary became:

```text
Makefile / project.sh / project.ps1
                |
                | bootstrap only
                v
        compatible Python starts
                |
                v
          scripts/repo.py
                |
                v
       shared environment policy
```

### Authority handoff

Under Conda, shell activation represents authority state. Therefore a compatible bootstrap Python may need to hand execution to the active Conda interpreter before policy-sensitive work proceeds.

This was implemented as a single-pass handoff rather than duplicated command logic.

## 9. Phase 4 — v0.5.0

Boundary:

```text
5ce2357 merge: phase 4 dual Python authority
```

Phase 4 was developed in explicit sub-blocks.

### 4A — policy/model

The environment model was expanded to support:

```toml
authority = "uv"
```

or:

```toml
authority = "conda"
```

without changing the Makefile API.

### 4B — native uv executable + managed Python

Native uv authority uses the executable found on PATH and resolves a uv-managed Python matching the configured request.

Final discovery arguments:

```python
[
    "python",
    "find",
    policy.python_request,
    "--managed-python",
    "--system",
    "--no-python-downloads",
    "--no-project",
]
```

### 4C — bootstrap and provenance

Under native uv:

1. require native uv;
2. install the configured Python request if needed;
3. resolve the managed Python;
4. create the project `.venv` from that interpreter;
5. record uv-specific provenance.

Conceptual provenance:

```json
{
  "source_authority": "uv",
  "source_python": "...uv-managed-python...",
  "source_python_version": "3.12.15",
  "source_uv_request": "3.12",
  "uv_invocation": ".../uv"
}
```

### 4D — lifecycle

The dispatcher, sync, lock, rebuild, and doctor were made authority-aware.

A major design distinction remained:

- Conda is active shell state and may require dispatcher handoff.
- Native uv is explicit executable/interpreter resolution and does not pretend to be an activated shell environment.

### 4E — four-lane proof

The final CI matrix became:

```text
Linux   / Conda / Make
Linux   / uv    / Make
Windows / Conda / Make
Windows / uv    / Make
```

All four lanes execute the same repository lifecycle:

```text
make setup
make check
```

Only runner preparation differs.

## 10. Phase 4 failure: uv authority contaminated by project .venv

The first four-lane proof exposed an important bug.

### Symptom

Native-uv lanes successfully installed Python 3.12.15, created `.venv`, and wrote provenance.

Immediately afterward the next lifecycle command failed:

```text
ERROR: project .venv provenance does not match the configured Uv Python authority.
Run: make env-rebuild
```

This happened on both Linux and Windows.

### Why fail-closed behavior was correct

The provenance check was doing its job.

The mistake was not in provenance comparison. The mistake was in authority rediscovery after `.venv` existed.

The authority Python recorded during bootstrap was the uv-managed installation.

Later, `uv python find` could see the project environment and resolve the project `.venv` instead.

The repository then correctly noticed:

```text
recorded source authority Python != newly resolved authority Python
```

### Fix

Managed-Python authority discovery was changed to include:

```text
--system
```

Final command shape:

```text
uv python find 3.12   --managed-python   --system   --no-python-downloads   --no-project
```

The key invariant became:

> The project venv may never become the source authority merely because it now exists.

### Corrective commit

```text
e29b2aa phase 4E: keep uv authority outside project venv
```

### Validation

The corrected Phase 4 run passed, followed by documentation closeout, PR validation, and post-merge dev validation.

## 12. Windows failure: env-rebuild tries to delete its own interpreter

The command was executed from an active project venv:

```text
(python-scaffolding) (.venv) PS ...> make env-rebuild
```

The dispatcher was therefore running from:

```text
M:\ATOL\GitProjects\python_scaffolding\.venv\Scripts\python.exe
```

The implementation tried:

```python
if VENV.exists():
    print(f"Removing {VENV}")
    shutil.rmtree(VENV)
```

On Windows this failed because the executable being deleted was still executing.

### Actual error

```text
Removing M:\ATOL\GitProjects\python_scaffolding\.venv
Traceback (most recent call last):
  ...
  File "...\shutil.py", line 633, in _rmtree_unsafe
    os.unlink(fullname)
PermissionError: [WinError 5] Access is denied:
'M:\ATOL\GitProjects\python_scaffolding\.venv\Scripts\python.exe'

make: *** [Makefile:40: env-rebuild] Error 1
```

### Why CI had missed it

Unix permits unlinking an executable that is currently running. Windows does not.

The original CI lifecycle validated bootstrap, provenance, and commands, but it had not intentionally activated the project `.venv` and then asked that interpreter to delete itself.

Real-machine validation exposed a platform process-lifetime invariant that unit tests alone had not modeled.


and then escape to an authority Python outside `.venv`.

This solved the file lock.

## 14. The PowerShell prompt overlay bug

The first hotfix caused the original foreground command to terminate before all replacement-process output was finished.

### Observed output

The key sequence looked like this:

```text
(python-scaffolding) (.venv) PS ...> make env-rebuild
Python 3.12 is already installed
(python-scaffolding) (.venv) PS ...> Removing M:\ATOL\GitProjects\python_scaffolding\.venv
+ ...python.exe ...\scripts\bootstrap.py
...
```

The PowerShell prompt had already returned even though rebuild output continued.

The problem became unmistakable when another command was typed while doctor output was still arriving:

```text
(python-scaffolding) (.venv) PS ...> $LASTEXITCODE
0env_source_conda_prefix=<not recorded>
(python-scaffolding) (.venv) PS ...>
venv_source_matches_authority=True
venv_python_version_matches_authority=True
...
```

Functionally, the rebuild eventually succeeded.

Operationally, the CLI contract was broken.

A foreground command must not return the prompt while it is still producing output.

### Root cause

The first design optimized for releasing the Windows executable lock, but process replacement changed the parent/child synchronization seen by Make and PowerShell.

The shell believed the foreground recipe had completed while replacement work was still active.

This demonstrated that two invariants had to be satisfied simultaneously:

1. the old `.venv\Scripts\python.exe` process must fully exit before deletion;
2. a stable foreground parent must remain alive and wait for the complete rebuild.

## 15. Final Windows fix: PowerShell owns process lifetime

The final design moved process-lifetime coordination to the PowerShell adapter while keeping environment policy in Python.

### Stable flow

```text
                    PowerShell / Make
                           |
                           | remains foreground parent
                           v
               old .venv Python resolver
                           |
                 resolves safe authority Python
                           |
                    resolver exits
                           |
             Windows executable lock released
                           |
                           v
                  authority Python
                           |
                      delete .venv
                           |
                      bootstrap
                           |
                        sync
                           |
                       doctor
                           |
                           v
                command exits completely
                           |
                           v
                  PowerShell prompt
```

### Makefile boundary

On Windows only, destructive rebuild is routed through PowerShell:

```make
PYTHON ?= python
POWERSHELL ?= powershell
PROJECT_CLI := $(PYTHON) scripts/repo.py

ifeq ($(OS),Windows_NT)
ENV_REBUILD_CLI := $(POWERSHELL) -NoProfile -File project.ps1 env-rebuild
else
ENV_REBUILD_CLI := $(PROJECT_CLI) env-rebuild
endif

env-rebuild:
	@$(ENV_REBUILD_CLI)
```

Other public commands continue to use the ordinary Python dispatcher.

### Private resolver

`scripts/env_rebuild_target.py` resolves the interpreter that is allowed to perform the destructive rebuild.

Core behavior:

```python
def prepare_rebuild_python() -> Path:
    if POLICY.authority == "conda":
        prefix = active_authority_prefix(POLICY)
        python = authority_python_path(POLICY, prefix)
        ...
    else:
        uv = require_native_uv(POLICY)
        completed = subprocess.run(
            [str(uv), *uv_python_install_args(POLICY)],
            cwd=ROOT,
            capture_output=True,
            text=True,
            check=False,
        )
        ...
        python = resolve_uv_managed_python(POLICY, uv_executable=uv)

    if inside(python, POLICY.venv):
        raise EnvironmentContractError(
            "env-rebuild authority Python resolved inside the project .venv"
        )

    return python
```

The resolver is still Python because Python owns environment policy.

PowerShell is not taught how uv or Conda authority works.

### PowerShell coordination

The PowerShell adapter handles the destructive command specially:

```powershell
if ($CommandArgs.Count -eq 1 -and $CommandArgs[0] -eq "env-rebuild") {
    $RebuildPythonOutput = & $PythonBin "scripts/env_rebuild_target.py"
    $TargetExitCode = $LASTEXITCODE

    if ($TargetExitCode -ne 0) {
        $ExitCode = $TargetExitCode
    }
    else {
        $RebuildPython = [string]($RebuildPythonOutput | Select-Object -Last 1)
        $RebuildPython = $RebuildPython.Trim()

        if ([string]::IsNullOrWhiteSpace($RebuildPython)) {
            [Console]::Error.WriteLine(
                "ERROR: env-rebuild target resolver returned no Python executable."
            )
            $ExitCode = 2
        }
        else {
            & $RebuildPython "scripts/repo.py" @CommandArgs
            $ExitCode = $LASTEXITCODE
        }
    }
}
```

The short resolver must finish before the second Python begins.

That is what releases the Windows executable lock.

PowerShell itself remains alive the whole time and waits for the second Python to finish.

That is what prevents the prompt overlay.

### Defensive Python guard

The Python dispatcher also refuses the unsafe direct path on Windows:

```python
if IS_WINDOWS and inside(sys.executable, VENV):
    raise SystemExit(
        "ERROR: Windows env-rebuild cannot delete the project .venv while "
        "running from its Python. Use: make env-rebuild "
        "(or .\\project.ps1 env-rebuild)"
    )
```

The unsafe path therefore cannot silently reappear later.

## 16. CI regression coverage for the Windows bug

The hotfix did not stop at unit tests.

Windows CI now intentionally simulates the dangerous state:

```powershell
$env:VIRTUAL_ENV = "$PWD\.venv"
$env:PATH = "$env:VIRTUAL_ENV\Scripts;$env:PATH"
make env-rebuild
```

This occurs after `make setup`.

Therefore Windows CI now proves that:

- the project venv exists;
- the project venv Python wins normal PATH resolution;
- `make env-rebuild` can destroy and recreate that same environment;
- the command returns normally;
- subsequent quality gates still pass.

This converts a Pangaea-only discovery into automated regression coverage.

## 21. Conda remains first-class

The stable release does not treat Conda as deprecated.

Under Conda authority:

- the active Conda environment chooses the source Python;
- policy-sensitive commands may hand execution to the active Conda Python;
- project uv operations use that authority interpreter through `python -m uv`;
- the project venv records Conda provenance.

Under native uv authority:

- native uv is resolved explicitly;
- the configured managed Python is installed/resolved;
- no fake active-environment model is created;
- the project venv records uv provenance.

Both modes share:

- Makefile vocabulary;
- project venv boundary;
- fail-closed provenance;
- test/lint/run behavior;
- Linux/Windows CI.

## 23. Why v1.0.0

The project could have continued indefinitely as “Phase 5.”

That would obscure whether the scaffold had ever reached a stable contract.

`v1.0.0` instead records a clear baseline:

- architecture extracted;
- bootstrap boundary explicit;
- project tests exist;
- cross-platform CI exists;
- both Python authority modes work;
- native uv is the default;
- real Windows migration was validated;
- the destructive Windows rebuild bug is fixed;
- its first attempted fix and second-order prompt bug are understood;
- the corrected behavior is automated in CI.

Future work should now be justified by actual use of the scaffold rather than by the existence of another roadmap number.
